- Development/testing authorization is narrower than product capability: on the host, only inspect UI and discover disk/partition/volume metadata with fixed WMI SELECT queries. Never execute partition previews that call storage methods, mutations, raw-device I/O, sector reads, mounts, initialization, formatting, repair or attribute changes against host disks/volumes. - Real mutation tests run ONLY inside DiskStudio-Test on DS-TEST-A-0001 and DS-TEST-B-0001 (two disposable 16 GiB NVMe disks). Never perform partition operations on the 80 GiB guest OS disk. Isolation checks live in scripts/vm, not the production app. Before tests validate the QMP VM name/UUID, exact file-backed disk inventory and capacities; confirm guest target serials, including the full namespace-1 suffix if reported. No host-device passthrough, shares or clipboard.
- The production partition backend uses fixed Windows Storage methods and provider-derived object references. Frontend commands accept typed operations, opaque disk identities and single-use confirmation tokens; never paths, WQL or method names. Metadata commands take no input. Revalidate unique disk identity, cross-provider identity, complete layout, protection flags and volume association at preview and execution. Fail closed on ambiguity, stale state or missing protection metadata. Verify postconditions, never automatically retry a mutation or claim transactional rollback.
- Judge capabilities per partition and operation, not by the presence of Windows elsewhere on a disk. GPT Windows data partitions support create/delete/NTFS format/resize; the running Windows partition supports only Windows-approved NTFS resize. Never format/delete running Windows, EFI, reserved, hidden, offline, read-only, clustered or paging-file targets. GPT Linux data/swap entries support deletion; creating a Linux entry does not create an ext4 filesystem. Unknown states fail closed. MBR and Linux filesystem editing remain unsupported and visibly explained.
- Imported RAW/IMG files remain read-only. The shipped application has no sample disks, simulated operations, sample workspace import/export, mock files, sample history or unfinished recovery/backup pages. Historical model fixtures live only in tests; Rust simulation helpers compile only under cfg(test). Do not reintroduce demo commands into Tauri IPC.
- The user now requests implemented file recovery, backup/restore and cloning. Explicit data jobs may use raw device I/O in the production backend; never invoke those jobs on host disks during development. On the host only build, run synthetic tests and inspect UI/metadata. All real scans, raw reads, backups and writes are tested exclusively on the VM A/B disks. No automatic scan, device access on page entry, elevation or host/VM product edition split.
- Data jobs bind opaque disk identity + layout, cross-check WMI providers, then verify opened device number, capacity, sector size and serial. Output files are selected in Rust native dialogs, never through frontend paths. Export/backup must use another physical disk. Clones reject same-disk and mismatched-scope/size/sector selections. Lock volumes for consistent copies; destinations are taken offline and left offline, including failure/cancellation. Readback SHA-256 is mandatory. No automatic rollback/retry or automatic activation of duplicate GPT identities.
- NTFS/FAT/exFAT recovery and signature carving must report actual candidates and limitations, never promise intact deleted contents. FAT deleted files are contiguous-free-cluster candidates; exFAT deleted fragmented chains are unsupported. Revalidate directory records, boot identity and allocation state before export. NTFS compressed/EFS exports, Ext recovery, resizing clones and proprietary DiskGenius backup formats are not implemented.
- Version 2 backups use bounded parallel Zstd compression, SHA-256 per chunk and a full logical-content digest. Incremental parents are immutable open handles selected in native dialogs, bound by manifest digest; chains are limited to 16 layers. Verify the complete chain before opening a writable target. Version 1 restore remains supported. VSS uses nonpersistent autoreleased FILE_SHARE_BACKUP snapshots of selected NTFS data partitions only; it provides filesystem consistency, not application-writer/transaction consistency. Never create VSS snapshots on the host during development. Capability implementation and VM acceptance are separate; do not imply acceptance before tests pass.
- Exception for known Linux GPT data/swap deletion: Windows can report hidden=true with read-only/shadow-copy=NULL for these non-Windows types. Permit those exact unavailable attributes while rejecting explicit true, requiring boot/system/offline=false, and enforcing disk-level protections. Do not generalize this exception to Windows, EFI, reserved or unknown types.
- Do not infer filesystems or usage from partition GUIDs. Keep unavailable data unknown, distinguish Windows status from SMART health, and never persist hardware metadata in local storage or development logs.
- Approved UI: no separate title bar; implemented product pages at top, disks only at left, partition map/table and contextual actions in the main pane. Name the page 磁盘管理. Do not add 镜像实验室, 仅镜像模式 or 示例磁盘 labels. Top 磁盘 menu contains image open/close and disk refresh. Opened images join the main disk list. Settings contains preferences, not image tools. Only ship navigation entries for implemented features.
- Run frontend build, domain tests, Rust core/application tests, VM-tool tests and a desktop build for relevant changes. Verify the actual native UI. Build once, verify matching SHA-256 of local executable and VM payload, then test real operations only inside the guest. Ordinary automated tests use synthetic models and never query or modify hardware.
- Latest scope addition: implement ext4 formatting and data-preserving end-boundary resize using the same production Windows executable. Ubuntu QEMU is authorized for independent verification on the same A/B virtual disks, never concurrently attached to both VMs. Ubuntu UUID/serial/capacity checks and read-only seed media stay in scripts/vm; all VM assets remain in .vm. The older statement above that Linux filesystem editing is unsupported is superseded only for the ext4 scope below.
- ext4 is limited to ordinary, non-system GPT Linux data partitions, cleanly unmounted ext4 with 4 KiB blocks and a checked feature allowlist. A GPT type only enables explicit inspection; never infer ext4 or automatically probe devices during inventory. Reject swap, protected/ambiguous targets, unsupported features and damaged/dirty filesystems. Native e2fsprogs receives one verified inherited device handle and a bounded extent, no arbitrary device/path input. Confirm once, lock all volumes, verify retained volume handles against native extents, revalidate metadata, then acquire an exclusive device handle and take the disk offline. Grow the partition before growing the filesystem; shrink the filesystem before shrinking the partition. Keep the disk offline on success/failure, verify GPT fields and filesystem, report partial failure without automatic retry or rollback. Feature implementation and VM acceptance must be recorded separately.
